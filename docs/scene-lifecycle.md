# 场景 × 生命周期：分场景 / 场前编排 / 临场使用

> 版本 v0.1 ｜ 2026-11-04 ｜ 状态：结构设计稿
> 上游：[氛围体系](ambience-system.md)（8 轴 + 场合卡 + 12 条规则）
> 解决的问题：同一套词表要服务三种完全不同的使用状态，混在一起做会导致"哪个场景都用不顺"。

---

## 0. 一句话结论

**分场景是"选哪种场合"，场前编排是"把这一场排好"，临场使用是"现场改得动"。**
三者共用同一套轴与规则，但输入、输出、界面、成功标准、失败代价完全不同——必须分三段设计，不能做成一个界面。

| 维度 | ① 分场景 | ② 场前编排 | ③ 临场使用 |
|---|---|---|---|
| 用户状态 | 还没想清楚 | 有时间、可思考 | 没时间、在场上、可能一手拿手机 |
| 时长 | 10 秒 - 2 分钟 | 10 - 40 分钟 | 持续 30 分钟 - 6 小时 |
| 主要设备 | 手机 | 桌面 / 平板（次要手机） | 手机（单手） |
| 核心问题 | "我这是哪种场合？" | "这一晚怎么排？" | "现在这首不对，怎么改？" |
| 系统输出 | 场合卡 + 参数区间 | 歌单 + 顺序 + 理由 + 校验报告 | 下一首建议 + 微调动作 |
| 成功标准 | 选对卡（一次命中） | 排完不用大改 | 不冷场、不砸场 |
| 失败代价 | 低（重选即可） | 中（重排 10 分钟） | **高（现场翻车不可逆）** |
| 允许的智能程度 | 可让模型猜 | 可让模型生成、人工修 | **只能规则化，不许即兴** |

这条"临场只许规则、不许模型即兴"是硬约束。场上没有重试机会。

## 1. 三段的信息流

```
① 分场景                     ② 场前编排                     ③ 临场使用
人话输入                     场合卡（已锁定）                 锁定歌单（只读）
   ↓                            ↓                              ↓
匹配/新建 场合卡  ──────►  生成 plan（顺序+理由）  ──────►  现场盘（下一首+微调）
   ↓                            ↓                              ↓
8 轴区间确认                 校验通过 → 锁定                 RunEvent（跳过/推/收/锁）
                                  ↓                              ↓
                             导出：清单/理由/预演            复盘 → 回填场合卡
```

关键设计：**②的输出是③的唯一输入**，③不允许自由选歌，只能"在已验证的池子里微调"。这是现场可靠性的来源。

## 2. ① 分场景：把"我这是哪种场合"变成一次命中

### 2.1 输入方式（按成本排序，都保留）

| 方式 | 例子 | 适用 |
|---|---|---|
| 选场景族 | 工作 / 商业空间 / 聚会 / 仪式 / 居家 / 运动 / 通勤 | 90% 情况，2 次点击 |
| 补充修饰 | "别太吵""别放太熟的""要有女声" | 落在轴上变成区间收窄 |
| 一句话 | "周六下午咖啡馆，客人不多" | 交给解析，落到最近卡 + 差量提示 |
| 从参考曲出发 | "像这首，但更安静一点" | 反查该曲轴值，±1 档生成新卡 |

### 2.2 场景库结构（三层，避免卡片爆炸）

```
场景族（7-9 个，稳定）
  └ 场景（族内 3-6 个，可增删）
      └ 场合卡（具体化：时段 × 人群 × 约束，canonical 后复用）
```

示例（商业空间族）：

| 场景 | 场合卡示例 | 关键差异 |
|---|---|---|
| 咖啡馆 | 周六下午 / 工作日早高峰 / 打烊前 | 交谈负荷 2，能量 3-4 vs 2-3 |
| 零售 | 买手店 / 便利店 / 书店 | 熟悉度与锐度不同 |
| 餐饮 | 午餐快翻台 / 晚餐慢食 / 酒吧过渡 | 能量曲线 ramp vs plateau |

**规则：场景可以多，场合卡 canonical 前必须过一致性测试（见 §6）。** 否则卡片会变成没人用的装饰。

### 2.3 输出：一张卡 + 三个确认

- 卡名（人话）："周六下午咖啡馆"
- 参数区间（人话化）：能量 3-4 · 可交谈 · 纯器乐为主 · 别太熟
- 一句话理由："客人以聊天为主，音乐让位给对话"
- 三个确认：对 / 改一点（滑轴）/ 换一张

### 2.4 失败模式与对策

| 失败 | 表现 | 对策 |
|---|---|---|
| 卡太多选不出 | 列表 30 张，用户放弃 | 只展示 7-9 族；族内按"最近使用 + 时段"排序 |
| 匹配错 | "婚礼"匹配到"派对" | 仪式类必须有二次确认（硬约束差异大） |
| 用户说不清 | "就……正常那种" | 默认卡 + 一句"我先按 XX 排，随时改" |

## 3. ② 场前编排：把卡变成一份能执行的 plan

### 3.1 流程（六步，每步可回退）

1. **定卡**：从①带入，或新建（新建后回写场景库）
2. **定时长**：30 / 60 / 90 / 120 / 240 分钟，或"到几点结束"
3. **生成**：按 12 条规则 + 能量曲线生成顺序（BPM 差 ≤6、Camelot 相邻、硬约束过滤）
4. **人改**：拖拽换序、替换单曲、锁定某几首（"这首必须在第 3 位"）
5. **校验**：跑规则检查，列出违规项（如"第 7→8 首 BPM 差 9"），一键修复
6. **锁定/导出**：生成只读 plan + 理由卡 + 打印清单；可选"预演"（按时间轴试听前 30 秒）

### 3.2 编排界面（桌面优先，三栏）

```
左：曲池（按轴筛选：能量/人声/熟悉度/锐度）   中：时间线（能量曲线可视化）   右：校验与理由
```

中栏是核心：横轴时间、纵轴能量，曲目是点，曲线是约束。**用户看到的不是"歌单"，是"一条能量曲线"**——这是与所有播放列表产品的界面差异。

### 3.3 校验规则（与体系 R-01~R-12 同源）

| 检查 | 阈值 | 提示语（人话） |
|---|---|---|
| 相邻 BPM 差 | ≤6 | "第 7、8 首差 9 BPM，接起来会飘" |
| Camelot 相邻 | 同调 / ±1 / 关系调 | "这两首调性打对台，中间建议插一首过渡" |
| 曲线符合度 | 与卡片曲线型一致 | "你说要爬坡，但第 5 首掉下去了" |
| 硬约束 | 0 违规 | "这首有脏话，与卡片约束冲突" |
| 时长偏差 | ±10% | "排了 52 分钟，比你要的 60 少 8 分钟" |
| 重复度 | 同艺人 ≤2 首/小时 | "同一个歌手连着两首，换一首？" |

### 3.4 输出物（可交付，不是只存在 App 里）

- `plan.json`（含轴值、规则版本、理由）
- 人读清单（Markdown / 打印）
- 播放清单（深链列表，一键逐首唤起）
- 分享卡（"周六下午咖啡馆 · 14 首 · 能量 3-4"，可发给同事）

### 3.5 成功指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 生成可用率 | 生成后未做结构性改动（换序 ≤2 首） | ≥ 50% |
| 编排耗时 | 从定卡到锁定 | ≤ 10 分钟（60 分钟场） |
| 校验修复率 | 违规项被处理的比例 | ≥ 90% |

## 4. ③ 临场使用：现场只做减法

### 4.1 硬约束（先立规矩）

1. **只读池**：现场只能在已锁定的 plan 内调整，不引入未验证曲目。
2. **禁止即兴**：无模型生成、无自由搜索；所有动作是确定性规则。
3. **单手可操作**：主要动作在屏幕下半区，单拇指可达，暗光下高对比。
4. **离线可用**：plan 与音频元数据本地缓存；无网只损失"跳转播放"以外的功能。
5. **误触可逆**：任何调整 3 秒内可撤销。

### 4.2 现场盘信息（一屏，最多 5 个数字）

```
剩余 47 分钟 ｜ 现在：第 6/14 首 ｜ 能量 4 ｜ 下一首：+1 档 → 5
[ 更炸 ]  [ 收一点 ]  [ 换人声 ]  [ 跳过 ]  [ 锁定当前风格 ]
```

- **剩余时间**：由 plan 时长与实际消耗推算，是现场最重要的数字
- **能量当前位置 vs 目标曲线**：一眼看出"超前了还是落后了"
- **下一首预览**：曲名 + 变化方向（+1 档 / 同档 / -1 档）

### 4.3 五个动作（只做这五个，不做设置面板）

| 动作 | 语义 | 实现（确定性） |
|---|---|---|
| 更炸 | 接下来 3 首整体 +1 档能量 | 从池中按轴值筛 energy+1、BPM +4~8 的候选，重排后续 |
| 收一点 | 接下来 3 首 -1 档 | 同理反向 |
| 换人声 | 人声档位切换（器乐↔演唱） | 按 vocal 轴替换同能量候选 |
| 跳过 | 当前曲不放了 | 从下一首继续，曲线自动补偿 |
| 锁定风格 | 未来 20 分钟不再自动调整 | 冻结窗口 |

> 不做：BPM 微调、Key 变换、EQ、淡入淡出时长——那是 DJ 软件的事，我们只做"选与序"。

### 4.4 现场事件记录（为复盘与体系迭代服务）

```json
{"run_id":"run-xxx","plan_id":"plan-yyy","t":1234,
 "event":"nudge_up | nudge_down | vocal_switch | skip | lock | end",
 "track_before":"id","track_after":"id","reason":"用户主动"}
```

这些事件是**体系改进的唯一真实反馈**：跳过率高的卡要重审，nudge 频繁说明卡的区间定窄了。

### 4.5 成功指标（现场）

| 指标 | 定义 | 目标 |
|---|---|---|
| 跳过率 | 主动跳过曲目 / 总曲目 | ≤ 15% |
| 调整次数 | 每小时 nudge 次数 | 1-3 次（0 次可能是没在用，>5 次说明排错了） |
| 完成率 | 按 plan 时长放完的比例 | ≥ 80% |
| 冷场事故 | 出现静音/明显不合场合 | 0 |

## 5. 状态机与数据模型

```
[card:draft] ──► [card:canonical]
      │                  │
      └──► [plan:draft] ──► [plan:locked] ──► [run:active] ──► [run:ended] ──► [review]
                                  ▲                              │
                                  └──────── 复盘回写（改卡/改规则）┘
```

新增字段（相对 ambience-system 的契约）：

| 对象 | 新增字段 | 说明 |
|---|---|---|
| `plan` | `locked_at`、`rule_version`、`curve_type`、`total_min`、`pins[]` | 锁定后不可变，改则生成新版本 |
| `run` | `started_at`、`ended_at`、`device`、`offline` | 一次现场执行 |
| `run_event` | `t`、`event`、`track_before`、`track_after` | 见 §4.4 |
| `review` | `skip_rate`、`nudges_per_hour`、`notes` | 复盘结论，回写场合卡 |

**不可变原则**：`plan:locked` 之后任何修改都产生新 plan（版本号 +1），保证现场与复盘可对照。

## 6. 三段共用的验收（防止各做各的）

| 检查 | 适用阶段 | 门槛 |
|---|---|---|
| 场合卡字段一致率 | ① | ≥ 80%（10 人独立填） |
| 生成可用率 | ② | ≥ 50% 无需结构改动 |
| 现场 5 动作可用性 | ③ | 单手 3 秒内完成，误触率 ≤ 5% |
| 跳过率 | ③ | ≤ 15% |
| 复盘回写率 | ③→① | 每场至少一条卡修正建议 |

## 7. 本期不做（延续 research.md §7）

| 不做 | 理由 |
|---|---|
| 现场实时 BPM 分析 / 节拍匹配 | DJ 软件领域，且现场不允许算法不确定 |
| 现场自由搜索加歌 | 破坏"只读池"可靠性；确有需要时走"暂停 → 解锁 → 加歌"显式流程 |
| 多人协同编排 | 先验证单人闭环 |
| 自动混音/无缝过渡 | 与 DJ.Studio 正面冲突，且技术上属另一赛道 |
| 桌面端专业导出（rekordbox XML 等） | 目标用户不用专业软件 |
