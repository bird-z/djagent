# 知识库架构：预设 + 生长 + 审核 + 检索

> 版本 v0.1 ｜ 2026-11-04 ｜ 状态：架构设计稿
> 上游：[PRD v2.0](PRD.md) ｜ [氛围体系](ambience-system.md)（8 轴与场合卡定义） ｜ [三段生命周期](scene-lifecycle.md)
> 本文回答：知识从哪来、怎么长、怎么审、agent 怎么查、查到后怎么答、答完怎么播。

---

## 0. 核心设计（四句话）

1. **知识分三层**：公共仓（官方 + 审核过的社区贡献）、团队仓（企业内部共识）、个人仓（个人风格），**检索时三层叠加，优先级个人 > 团队 > 公共**。
2. **一切贡献走同一条流水线**：草稿 → 自动校验 → 人工审核 → 发布，**未发布的内容只能自己用，不能进公共检索**。
3. **agent 的回答必须有证据**：每条推荐都要能指回知识库里的具体记录（曲目 ID / 场合卡 ID / 规则号），禁止"凭感觉生成"。
4. **播放是回答的一部分**：回答里带深链，用户点一下直接在酷狗播放（已验证），不是"给你个歌名自己搜"。

## 1. 三层知识库

```
┌─────────────────────────────────────────────────────────┐
│ 公共仓 Public KB        官方策展 + 审核通过的社区贡献      │
│   · 全部用户可检索   · 改动需审核   · 版本化，可回滚       │
├─────────────────────────────────────────────────────────┤
│ 团队仓 Team KB          企业/组织内部共识（B 端核心）      │
│   · 组织成员可检索   · 管理员审核   · 可继承公共仓并覆盖   │
├─────────────────────────────────────────────────────────┤
│ 个人仓 Personal KB      个人风格、私藏、临时标注           │
│   · 仅本人可检索     · 无需审核     · 可一键提交到上层     │
└─────────────────────────────────────────────────────────┘
```

**继承与覆盖规则**（避免三份数据打架）：

| 情况 | 处理 |
|---|---|
| 个人仓与公共仓对同一首歌标注不同 | 个人优先，但回答中标注"按你的偏好调整" |
| 团队仓覆盖公共仓某张场合卡 | 团队优先，记录 `overrides: card_id@version` |
| 公共仓更新了被个人引用的卡 | 不自动覆盖个人，提示"公共版已更新，是否同步" |
| 同一首歌在多层都有 | 元数据取 `confidence` 最高者，理由取当前层 |

**为什么必须分层**：个人偏好不该污染公共数据，企业共识不该被个人覆盖，公共数据不该被随意改动——这是三个不同的治理主体。

## 2. 知识对象（五类）

| 对象 | 内容 | 来源 | 审核 |
|---|---|---|---|
| `track` 曲目 | hash、歌名、艺人、BPM、Camelot、8 轴值、confidence、source | 预设 + 抓取 + 用户贡献 | 公共仓需审核，个人仓不需要 |
| `venue_card` 场合卡 | 见氛围体系 §4.1（含 rationale/status） | 官方预设 + 用户新建 | 公共仓需审核 |
| `rule` 规则 | 编号、条件、结论、理由、版本 | 官方维护 | 仅官方，不接受 UGC |
| `plan` 编排 | 曲目序列 + 理由 + 规则版本 | 系统生成 + 用户手改 | 可选分享到公共（"这张歌单不错"） |
| `note` 说明/理由 | 人话解释、场合描述、使用心得 | 官方 + 用户 | 公共仓需审核 |

**关键约束**：`rule` 不接受 UGC。规则是判断层的法律，只能官方版本化修订——否则一致性无法保证。

## 3. 冷启动：预设知识库该有多大

不是"越多越好"，是"覆盖度够用"。目标（v1.0 上线时）：

| 维度 | 目标 | 理由 |
|---|---|---|
| 曲目数 | **300-500 首** | 覆盖 9 类场合 × 每类 30-50 首候选，保证同一卡可排出 60 分钟不重复 |
| 场合卡 | **9-15 张** | 覆盖 9 类场合，热门类（商业空间/工作）各 2-3 张变体 |
| 规则 | **12 条** | 见氛围体系 §5，宁少勿乱 |
| 元数据完整率 | **≥95%** | BPM/Camelot/8 轴缺一项，该曲不进公共检索 |
| 人工核对率 | **100%** | 预设阶段必须全量人工核对，不能靠推断 |

**覆盖度指标**（比总量更有意义）：

```
覆盖度 = Σ(每张 canonical 卡在目标时长内可生成的不重复歌单数) / 卡数
目标：每张卡 ≥ 3 套互不重复的歌单
```

只有 500 首但集中在 3 类场合，比 300 首均匀覆盖 9 类更糟。

## 4. 贡献与审核流水线

### 4.1 状态机

```
[draft] ──提交──► [auto_check] ──通过──► [in_review] ──通过──► [published]
   ▲                   │                    │                      │
   └────── 退回 ────────┘                    │                      │
                        └──── 退回 ──────────┘                      │
                                                             [deprecated] / [merged]
```

| 状态 | 谁能看到 | 说明 |
|---|---|---|
| `draft` | 作者 | 仅个人仓，可自由编辑 |
| `auto_check` | 系统 | 自动校验（§4.2），秒级，不通过直接退回并说明原因 |
| `in_review` | 审核队列 | 人工审核，SLA ≤ 48 小时 |
| `published` | 目标层可见 | 进入公共/团队仓检索 |
| `merged` | — | 与既有记录合并（同一首歌重复提交） |
| `deprecated` | — | 元数据错误或版权下架，保留记录不删除 |

### 4.2 自动校验（提交即跑，六项）

| # | 检查 | 不通过的处置 |
|---|---|---|
| 1 | 必填字段完整（hash/BPM/Camelot/8 轴/confidence） | 退回补全 |
| 2 | hash 格式（32 位十六进制）+ 酷狗存在性回查 | 退回"曲目不存在" |
| 3 | 重复检测（hash 精确 + 标题/艺人模糊 + 可选音频指纹） | 命中则转 `merged` 流程 |
| 4 | 元数据冲突（同曲 BPM 差 >5、Camelot 不一致） | 标记"待仲裁"，进人工 |
| 5 | 敏感内容（脏话、政治、违禁词、明显错误场合标注） | 直接拒绝并记录 |
| 6 | 版权标记（是否为未发行/翻录/盗版源） | 标记"仅个人可用" |

### 4.3 人工审核要点（审核员 checklist，5 分钟/条）

1. 这首歌确实适合所标注的场合卡吗？（听 30 秒）
2. 8 轴取值与术语卡一致吗？（尤其能量、人声两轴）
3. `rationale` 是人话、能说服人吗？
4. 有无更适合的既有记录被忽略？（避免重复）
5. 有无版权/合规风险？

**审核不是"看一眼通过"**，是"能否在一致性测试里站住"——所以审核员必须先通过术语卡标注考核（κ ≥ 0.6）。

### 4.4 信誉与激励

| 机制 | 规则 |
|---|---|
| 贡献分 | 通过 1 条 +10；被合并 +2；被驳回 -3（连续驳回 5 次进入冷静期） |
| 权限升级 | 累计 20 条通过 → 可申请"协审"；50 条 → 进入审核员候选 |
| 署名 | 公共仓记录 `contributors[]`，可展示 |
| 撤回 | 作者可随时撤回未发布内容；已发布内容需走 `deprecated` |

### 4.5 审核成本估算（决定能不能规模化）

- 单条 5 分钟 × 每日 200 条 = 16.7 小时/天 ≈ 2 名全职审核
- 因此**自动校验必须先拦住 70%+ 的低质提交**，否则人力撑不住
- 早期（<50 条/天）由团队成员兼审；超过后按"协审 + 抽检"模式（老用户审新人，官方抽检 20%）

## 5. Agent 检索与回答

### 5.1 检索工具（agent 可调用的 4 个动作）

| 工具 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `kb_search` | 结构化条件（场合/8 轴区间/关键词/BPM 区间） | 曲目列表 + 理由摘要 | 找候选 |
| `kb_card` | 场合描述或卡 ID | 匹配的场合卡 + 差量提示 | 定位场合 |
| `kb_compose` | 卡 ID + 时长 + 约束 | plan（曲目序列 + 理由 + 规则版本） | 生成歌单 |
| `kb_play` | 曲目 hash 或 plan | 深链（`kugou://start.weixin?cmd=212...`） | 直接播放 |

### 5.2 检索策略：结构化优先，语义兜底

```
用户一句话
   ↓
① 结构化解析：能不能直接映射到场合卡 / 8 轴区间？
   ├─ 能 → 结构化过滤（SQL/索引）→ 精确、可解释、毫秒级
   └─ 不能 → ② 语义检索（向量）→ 得到候选 → 再用结构化条件校验
   ↓
③ 排序：规则符合度（BPM/调性/曲线）> confidence > 熟悉度匹配
   ↓
④ 生成回答：每条带证据（曲目 ID + 轴值 + 规则号）
   ↓
⑤ 附播放动作：深链
```

**为什么结构化优先**：语义检索会"看起来像"，但不保证 BPM 接得上、调性不打架。**规则校验是最后一道闸，不能省。**

### 5.3 回答格式（强制模板）

```
【场合】周六下午咖啡馆（卡 vc-cafe-afternoon-1）
【方案】14 首 / 58 分钟 / 能量 3→4 平台型
【理由】客人以交谈为主（交谈负荷 2）→ 人声 ≤2、密度 ≤2（规则 R-01）
【前 3 首】
  1. 《X》 96 BPM · 8A · 纯器乐 · 冷门  ← 开场铺底，不抢谈话
  2. 《Y》 100 BPM · 9A · 气声    ← 与①同调相邻，人声轻
  3. 《Z》 104 BPM · 8A · 器乐    ← 回到 8A，能量 +1 档
[▶ 全部播放]  [复制歌单]  [为什么这样排]
```

三条硬要求：
1. 每个结论后必须有括号引用（卡 ID / 规则号 / 轴值）。
2. 找不到合适卡时必须说"没有匹配的场合卡，要不要新建一张"，**不许硬凑**。
3. 播放链接必须来自知识库记录，不许模型自己拼 hash。

### 5.4 "合理有价值"的判定标准（可测）

| 标准 | 度量 | 目标 |
|---|---|---|
| 有依据 | 回答中带证据的比例 | 100%（无证据视为不合格） |
| 接得上 | 相邻 BPM 差 ≤6、Camelot 相邻 | ≥ 95% |
| 场合对 | 用户未立即否定/换卡 | ≥ 80% |
| 能播 | 深链可唤起比例 | ≥ 95%（Android） |
| 不硬凑 | 无匹配时的正确拒绝率 | ≥ 90% |

## 6. 数据质量与演化

### 6.1 冲突合并（同一首歌多条记录）

```
优先级：人工核对(confidence=1.0) > 官方抓取(0.8) > 用户标注(0.5-0.7) > 模型推断(≤0.5)
合并策略：字段级取值（不是整条覆盖），保留所有来源与时间戳
不可合并项：同一 hash 但 BPM 差 >5 → 进仲裁队列
```

### 6.2 从行为中学习（隐式补充）

| 信号 | 含义 | 用途 |
|---|---|---|
| 跳过（<30 秒） | 这首不适合该卡 | 降低该曲在该卡的权重 |
| nudge（更炸/收一点） | 卡的能量区间定偏了 | 提示修订卡片区间 |
| 完整播放 | 正向 | 提升权重 |
| 手动替换某首 | 局部不适配 | 记录"卡内替代关系" |

**注意**：行为信号只用于**调整权重与提示修订**，不自动改元数据——自动改会让知识库漂移且无法追责。

### 6.3 知识腐败防治

| 风险 | 表现 | 对策 |
|---|---|---|
| 刷贡献 | 大量低质提交 | 信誉分 + 抽检 + 连续驳回冷静期 |
| 口味极化 | 公共仓被某一圈层占领 | 每张卡设"风格配额"（如 60% 主流 / 40% 长尾） |
| 元数据腐化 | 越改越乱 | 字段级版本 + 可回滚 + 仲裁队列 |
| 版权风险 | 收录盗版/未发行 | 提交时标记 + 定期抽检 + 下架流程 |

## 7. 技术形态（够用就好）

| 组件 | 选型建议 | 理由 |
|---|---|---|
| 存储 | SQLite（单机）/ Postgres（多人） | 结构化字段为主，事务与版本控制方便 |
| 全文索引 | FTS5 / Postgres GIN | 歌名、艺人、场合名模糊搜 |
| 语义检索 | 向量索引（可后置） | 只在结构化无法解析时启用，避免"语义漂移" |
| 版本 | 每对象 `version` + `changed_by` + `changed_at` | 可回滚、可审计 |
| 接口 | HTTP JSON（`/kb/search` `/kb/card` `/kb/compose` `/kb/play`） | agent 与前端共用 |
| 播放 | 深链（已验证） | 不碰音源 |

**不上向量库也能跑**：300-500 首规模，结构化过滤 + FTS 足够；语义检索是"当用户说话太模糊时的兜底"，不是主路径。

## 8. MVP 边界（本期做到哪）

| 做 | 不做 |
|---|---|
| 公共仓 + 个人仓两层（团队仓后置） | 团队/组织多租户 |
| 300 首预设 + 9 张卡 + 12 条规则 | 万级曲库 |
| 提交 → 自动校验 → 人工审核 → 发布 | 自动审核（AI 审核 AI） |
| 4 个检索工具 + 证据链回答模板 | 多轮复杂推理对话 |
| 深链播放（Android） | 站内播放器 |
| 行为信号用于权重调整 | 自动改元数据 |
