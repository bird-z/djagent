# kgJP 头脑风暴：场景 → 音乐 → 一键跳转酷狗

> 版本 v0.1 ｜ 2026-11-03 ｜ 状态：头脑风暴稿，未经取舍定稿

---

## 0. 先摊牌：三条已经验证过的事实

这一节是整份文档的地基。没有这三条，后面所有方案都是空谈。

**事实 A｜酷狗网页搜索结果里拿不到单曲 ID。**
实测抓取 `www.kugou.com/yy/html/search.html?searchKeyWord=晴天`，返回的条目只有「歌名 + 歌手 + 专辑链接 + 时长」。
条目里唯一的结构化 ID 是 `/album/info/<album_id>/`（专辑级），**没有 songid、没有 hash、没有 mixsong id**。
含义：如果坚持"精确定位到某一首"，光靠网页搜索这条路走不通，必须补一条 ID 获取通道。

**事实 B｜单曲页 URL 的构造规则是 `https://www.kugou.com/mixsong/<mixsong_id>.html`。**
`mixsong_id` 形如 `g7251h15`（g + 字母数字混合）。实测首页「新歌首发」栏目里的链接严格符合这个格式，且与歌曲一一对应。
含义：**只要拿到 mixsong_id，就能拼出可点开的播放页链接**。这是跳转的确定性锚点。

**事实 C｜当前的网络环境拦不住 curl，但 WebFetch 能通。**
直接 `curl msearchcdn.kugou.com` 被沙箱安全策略挡下（HTTP 000）。所以原型阶段的探测只能走 WebFetch 或换真实浏览器通道。
含义：**"在 Agent 对话里实时搜歌"这件事本身受工具链限制**，架构上不能假设"随时能查"，得留离线和缓存路径。

结论一句话：**能拼链接，但 ID 得另想办法拿；能拿 ID，但查询通道不稳定。** 这两条约束塑造了下面的方案分叉。

## 1. 产品定位的三种可能（必须先选一个）

同一个需求，落到三种完全不同的产品形态上。我把它们摆出来，因为它们决定了后面 80% 的工作量。

| | 形态 1：**插件/技能**（寄生在 Agent 里） | 形态 2：**本机常驻服务**（Agent 与服务协作） | 形态 3：**独立小工具**（跟 Agent 解耦） |
|---|---|---|---|
| 形态 | Agent 技能 + 协议处理器 | localhost 服务 + 系统协议注册 | 独立桌面/网页应用 |
| 用户动作 | 在对话里说"放首歌"，卡片出现，点一下 | 同上，但点击后唤起本机酷狗客户端 | 打开工具，输入场景，拿列表 |
| 覆盖端 | ad 端（对话界面）+ win/mac 需各自做壳 | 三端都能覆盖，但是三套安装包 | 三端都能覆盖 |
| 强点 | 与"提问即得"的原始诉求最贴合 | 能真正唤起客户端播歌，体验最爽 | 实现最简单，能先跑起来验证选曲质量 |
| 弱点 | 只能生成链接，落不到客户端播放 | 安装门槛高，协议注册在 mac/win 上各有一堆坑 | 脱离对话场景，价值打折 |
| 工作量（粗估） | 中 | 大（约 2–3 倍） | 小 |

**我的判断**：这不是三选一，而是应该**分层**。
先做形态 1 拿到"对话里出卡片"的核心价值，把形态 2 当作可选的增强件（协议唤起），形态 3 其实是形态 1 的一个调试台。
但如果你要的是"点了就必须在酷狗里开始播"，那形态 2 就是主线，形态 1 只是入口。**这个取舍你来定。**

## 2. 核心难点：场景 → 歌，靠什么决定（这是产品灵魂）

跳转是工程问题，选歌是产品问题。而选歌这一步最容易糊弄。我把可能的做法按"可解释性"排序：

### 方案 S1：情绪映射表（规则驱动）
把场景归到 8–12 个情绪标签（专注、疲惫、烦躁、怀旧、亢奋、孤独、治愈、行进感……），每个标签配一批候选曲。
- 强点：**完全可解释**，可以指着表说"因为你说的是深夜赶 deadline，我归到'疲惫但需要支撑'，配的是 X"。
- 弱点：标签之间的边界模糊，跨场景容易重复；曲库需要人工维护。
- 适用：第一版，最稳。

### 方案 S2：语义嵌入检索（向量驱动）
把场景描述编码成向量，在歌单/歌词的向量库里做最近邻。
- 强点：能处理"我说不清但我有感觉"的长尾场景。
- 弱点：**推荐结果难以解释**，容易出现"技术上相似、情绪上错位"；需要建索引和嵌入模型。
- 适用：S1 跑通后的升级件。

### 方案 S3：大模型直接给（LLM 生成）
让模型根据场景自由发挥，直接输出歌名+歌手。
- 强点：零维护，长尾覆盖最好，语气最自然。
- 弱点：**幻觉是真问题**——歌名对但歌手错、或者歌根本不存在；版权/曲库里没有。必须加"存在性校验"这一道闸。
- 适用：作为候选生成器，但**绝不能直接用它的话就上屏**。

### 方案 S4：混合（我的倾向）
LLM 负责"理解场景 + 给出 3–5 个候选（含推荐理由）"，规则表负责"约束（不要重复、避开用户已听、符合时长/语种偏好）"，校验层负责"这首歌酷狗里真的存在且 ID 能拿到"。
- 三层各司其职：**理解靠模型，约束靠规则，落地靠校验**。
- 强点：既解释得清，又不至于漏长尾。
- 弱点：链路长，任何一环挂了都要有降级。

### 关键的子问题：推荐理由怎么说
"给你一首《晴天》"是推送，"你连着改了三版还没过，先听个不带攻击性的"才是推荐。
我倾向强制模型为每首歌输出**一句不超过 30 字的理由**，且理由必须引用用户刚才说的具体内容（而不是"这首歌很适合放松"这种空话）。这一条能把产品质感拉开一个档。

## 3. 场景分类法：把"某个场景"拆细

你说要覆盖全部场景类型，那得先分类。我拆成四层，每层的选曲逻辑不同：

**L1 状态型**（写代码专注 / 烦躁 / 深夜加班 / 通勤）
→ 选曲看**节奏和能量曲线**，不看歌词内容。焦点是"不打断思路"或"托住情绪"。
→ 关键约束：专注场景禁用有强人声副歌的曲子（会抢注意力）。

**L2 创作型**（剪视频找 BGM / 写文案找氛围 / PPT 背景音）
→ 选曲看**功能和时长**。BGM 需要可循环、无人声、无版权雷；PPT 背景音需要低存在感。
→ 关键约束：**必须能说明"这段适合放在哪个位置"**（片头/转场/情绪推高）。

**L3 联想型**（聊到"雨""回家""毕业"顺手给一首）
→ 选曲看**语义关联和情绪对位**，自由度最高，也最容易给出惊喜或尴尬。
→ 关键约束：要容忍"不精准"，但绝不能给到破坏语境的歌（比如聊丧亲给一首欢快的）。

**L4 显式型**（"放点周杰伦""想听摇滚"）
→ 这是检索不是推荐。核心是**准确率和去重**，不需要理由，需要的是"点开就是那首"。

**设计启示**：L4 和 L1–L3 应该是**两套不同的管线**。L4 走检索、要 ID 精确；L1–L3 走推荐、要理由充分。硬塞进一套逻辑会导致两边都不好用。

## 4. 跳转链路：从"卡片"到"音箱响起来"的六种落法

按可靠性从高到低排：

| # | 落法 | URL 形式 | 唤起客户端？ | 精确到单曲？ | 可靠性 |
|---|---|---|---|---|---|
| J1 | 搜索页兜底 | `kugou.com/yy/html/search.html#searchKeyWord=<歌名 歌手>` | 否（纯网页） | 否，落在搜索结果 | ★★★★★ |
| J2 | 单曲页 | `kugou.com/mixsong/<mixsong_id>.html` | 否 | **是** | ★★★★（需 ID） |
| J3 | 官方协议 | `kugou://` 系列（需实机验证参数） | **是** | 视参数而定 | ★★（未验证） |
| J4 | web+ 协议 | `web+kugou://...` | 是，且能带 web 回退 | 视参数 | ★（未验证） |
| J5 | 本机服务中转 | `http://127.0.0.1:<port>/play?song=...` → 服务再唤起 | 是 | 是（服务内查 ID） | ★★★（需常驻） |
| J6 | 剪贴板/分享码 | 复制"歌名 歌手"让用户自己搜 | 否 | 否 | ★★★★★（但最差体验） |

**工程上我建议的降级链**：
`J5（有服务时）→ J3（协议可用时）→ J2（有 ID 时）→ J1（永远可用）`。
**J1 必须永远存在**，它是兜底中的兜底。哪怕所有花活都失效，用户点下去至少能看到搜索结果，不会出现"点了没反应"这种最伤信任的情况。

**一个容易被忽略的细节**：移动端和桌面端对 `kugou://` 的拦截策略不同。iOS 上未知 scheme 静默失败的概率很高，Android 上可能弹选择器。所以协议跳转**必须在 800ms 内做超时检测并回退到 J1**，否则用户面对的是死按钮。

## 5. 三端差异：这不是"一套代码三处部署"

| 维度 | ad 端（对话界面） | Windows | macOS |
|---|---|---|---|
| 载体 | 网页/内嵌卡片 | 需要壳程序 | 需要壳程序 |
| URL 唤起 | 受浏览器 scheme 白名单限制，最严 | 注册表 `HKCU\Software\Classes\kugou` | `Info.plist` CFBundleURLTypes |
| 客户端检测 | 无法检测 | 查进程/窗口类名 | `NSWorkspace` 查 bundle id |
| 权限坑 | 无 | 基本无 | Gatekeeper 公证、辅助功能授权（若要控制播放） |
| 静默失败 | 有，且无法感知 | 较少 | 有（未安装时） |
| 最省事的方案 | 纯 J1/J2 链接 | J3 协议优先 | J5 本机服务更稳（协议在这上面更活跃） |

**结论**：三端的差异主要在"**唤起**"这一步，"**选歌**"和"**拼链接**"应该共用一套逻辑（可以放本地，也可以放一个极轻的服务端）。
所以架构上应该切成：`选曲核心（共享）` + `端侧唤起适配器（三套）`。别为了共享而共享到唤起层，那会变成三端都别扭。

## 6. 十个容易被跳过的坑（都是会咬人的）

1. **幻觉歌**：模型给的歌名在酷狗里搜不到 → 必须有存在性校验，校验失败就降级成 J1 并如实告知"这首没找到，给你搜了同名"。
2. **同名撞车**：搜"晴天"能出 30 个版本（原版、Live、DJ、翻唱、钢琴版）。**必须锁"原版优先"策略**，否则用户点了听到的是不知名翻唱，信任直接归零。
3. **版权灰区**：有些歌酷狗有页面但无版权不可播。页面能打开 ≠ 能听。
4. **推荐过度**：用户只是在聊技术，没想听歌，你硬塞一首会烦。需要**触发阈值**：只在场景明确（情绪词、明确请求、明显疲劳信号）时才出，且**一次只给 1 首主推 + 2 首备选**，不要列表轰炸。
5. **重复推荐**：同一天问三次"想听点安静的"都给同一首，立刻显得很蠢。需要短期会话去重。
6. **理由通货膨胀**：每首都说"很适合你的心情"，等于没说。理由必须具体到引用原话。
7. **时机错位**：用户正在焦头烂额排错，你弹个音乐卡片 = 打扰。**紧急/负面高压场景要降权或不出**。
8. **协议劫持**：`kugou://` 在没装客户端时会静默失败，或者被别的程序抢注。必须有超时回退。
9. **ID 漂移**：mixsong_id 可能随曲库调整变化，硬编码会腐烂。要存"歌名+歌手+hash"多键，允许重查。
10. **静默失败**：最伤的是"点了没反应还不告诉我"。**任何失败路径都必须有可见反馈**，哪怕只是一句"没唤起客户端，已为你打开网页版"。

## 7. 反直觉的想法（先记下来，不一定做）

- **反着想：不做推荐，做"翻译"**。用户说"我现在这个状态"，你只回一个歌名，不给理由、不给链接列表。极简到像一个朋友递过来一只耳机。成本最低，气质最好——但跳转价值弱。
- **把歌单当"场景包"**：不做单曲推荐，做"深夜修 bug 40 分钟"这样一个场景歌单（5–8 首，按能量曲线排好）。用户点一次，是一段旅程而不是一首歌。对 L1 状态型特别合适。
- **反向入口**：不问"要听什么"，而是 Agent 发现自己要输出一大段代码/长文时说"这段比较长，要不要配个背景？"——把音乐变成输出行为的伴生品。
- **可解释性做到极端**：每首歌点击前就能看到"为什么是这首"，包括它命中了你的哪个词。做成一个可展开的小抽屉。透明度本身就是差异化。
- **失败也是产品**：没找到歌时，不要道歉，而是"酷狗里没这首，但我给你找了个同类的 Y"。
- **做减法**：三端里可能只有一端是真需求。先把一端做到无可挑剔，比三端都半吊子强。

## 8. 我建议的第一刀（如果要我拍板）

1. **形态**：先做形态 1（Agent 技能 + 卡片），跳转走 `J2/J1`（有 ID 用单曲页，没有就搜索页）。协议唤起作为 Phase 2。
2. **选曲**：S4 混合，但第一版只用 S1 情绪映射表 + 手工曲库（50 首左右），先验证"出的歌对不对味"，别急着上向量。
3. **场景**：先只做 L1 状态型 + L4 显式型。这两类最容易验证对错，L2/L3 留到有反馈之后。
4. **验证标准**：不看点击率，看"用户点了之后有没有真的听下去"。如果点了就切走，说明歌选错了，链接再准也没用。

## 9. 待你确认的四个问题

1. **唤起客户端是硬需求还是加分项？** 决定做不做本机服务。
2. **第一批场景能不能收窄到 L1+L4？** 全上会让第一版摊薄。
3. **曲库你手上有吗？** 还是要我从零建（会涉及版权信息准确性）。
4. **"ad 端"具体指什么载体？** 是我理解的 Agent 对话界面，还是某个具体的广告/投放端？这个词歧义太大，会影响端侧方案。
