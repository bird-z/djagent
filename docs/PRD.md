## 1. 一句话定位

**把"这是什么场合"翻译成"放哪些歌、按什么顺序、为什么"，然后一键放出来。**

给没做过 DJ 的人用的音乐判断工具。用户只说场合，系统负责翻译成参数与顺序，播放交给已有的音乐 App（首发酷狗）。

不做的定位澄清：不是播放器、不是曲库、不是 DJ 打碟软件、不是通用手机助手。

## 2. 用户与需求

### 2.1 目标用户

| 人群 | 典型场景 | 现有替代方案的不足 |
|---|---|---|
| 场合组织者（聚会/婚礼/团建） | "两小时，别冷场，别太吵" | 网易云场景歌单太泛，且不解释为什么 |
| 小店经营者（咖啡馆/买手店） | "每天同一时段，不能重复，不能吵" | 手动维护歌单，靠感觉，换人就走样 |
| 内容创作者 | "剪片找 3 首同气质、能量递进的 BGM" | 逐首试听，无法按参数筛 |
| 普通听歌用户 | "现在想听点对的" | 推荐黑盒，切歌率高 |

### 2.2 两类需求（必须分开满足）

| 类型 | 用户原话 | 本质 | 对应产品段 |
|---|---|---|---|
| **A 听着对** | "这场合放点什么好" | 场合 → 氛围 → 直接播 | ① 分场景 + ③ 临场 |
| **B 排得顺** | "这一晚怎么排、怎么接" | 曲目集合 → BPM/调性 → 顺序 | ② 场前编排 |

只做 A → 与场景电台同质；只做 B → 变成专业工具，小白不用。**A 是入口，B 是壁垒。**

## 3. 产品原则（不可协商）

1. **判断与执行分离**：判断层不认识界面与播放器；执行层不认识规则。换壳不影响判断。
2. **上层人话，下层参数**：用户永远不需要懂 BPM/Camelot。
3. **临场只许规则，不许即兴**：现场没有重试机会，所有现场调整必须是确定性规则。
4. **每个结论可回溯**：推荐理由必须能指回具体轴值 + 规则编号 + 规则集版本。
5. **共识先于算法**：词表与规则未达一致性门槛前，不上线任何"智能推荐"。
6. **不碰音源**：只做索引与跳转，不托管、不缓存、不解析音频流。

## 4. 产品结构（三层矩阵）

```
① 判断层（资产）  8 轴词表 + 场合卡 + 12 条规则 → HTTP / MCP / Skill
② C 端（获客）    H5/PWA：分场景 → 场前编排 → 临场使用 → 唤起酷狗
③ B 端（变现）    Web 控制台：多场地排程 · 卡片版本下发 · 播放监控 · 复盘
```

三层的关系：C 端验证价值，B 端收钱，判断层保证换壳不重做。

## 5. 功能需求

### 5.1 生命周期三段（需求编号 L1-L3）

| 编号 | 段 | 用户目标 | 关键约束 | 验收 |
|---|---|---|---|---|
| L1 | 分场景 | 10 秒内选定"我这是哪种场合" | 7-9 个场景族，卡片不超过 3 层 | 首次使用不卡在选卡（5 人可用性测试） |
| L2 | 场前编排 | 10-40 分钟排出一份能执行的 plan | 三栏界面（曲池/能量曲线/校验）；六项校验；锁定后不可变 | 生成可用率 ≥50%（换序 ≤2 首）、耗时 ≤10 分钟/60 分钟场 |
| L3 | 临场使用 | 现场改得动、不出事故 | 只读池、禁止即兴、单手可达、离线可用、3 秒可撤销 | 跳过率 ≤15%、调整 1-3 次/小时、冷场事故 0 |

### 5.2 判断层（P0，最高优先级）

| 编号 | 需求 | 产出 | 出口条件 |
|---|---|---|---|
| J1 | 8 轴受控词表定稿 | 术语卡（1 页） | 3 人评审通过 |
| J2 | 50 首双人盲标 | 标注数据集 | 有序轴加权 κ ≥ 0.60；场合类型 α ≥ 0.70 |
| J3 | 9 张 canonical 场合卡（覆盖 9 类场合） | 卡片库 | 10 人独立填字段一致率 ≥ 80% |
| J4 | 12 条映射规则定稿 + 版本号 | `ruleset-v1.0` | 盲评胜率 ≥ 70%（体系 vs 直觉） |
| J5 | 曲目元数据补齐（BPM/Camelot/8 轴） | `track` 数据集 | 抽样 20 首人工核对，元数据准确率 ≥ 90% |

### 5.3 C 端功能（按阶段）

| 编号 | 功能 | 阶段 | 说明 |
|---|---|---|---|
| C1 | 场景卡选择（族→场景→卡，4 种输入） | 阶段 1（H5） | 支持选族/加修饰/一句话/从参考曲出发 |
| C2 | 一键出歌单（≤3 秒） | 阶段 1 | 按卡片区间 + 规则生成 |
| C3 | 唤起酷狗播放（Android 优先） | 阶段 1 | 深链已真机验证；iOS 降级为复制深链 |
| C4 | 桌面编排台（三栏 + 能量曲线 + 校验） | 阶段 1 | 大屏场景，桌面排完生成二维码手机接场 |
| C5 | plan 交付（JSON / 清单 / 分享卡） | 阶段 1 | 可发给同事、可打印 |
| C6 | PWA 化（添加主屏 + 离线缓存） | 阶段 1.5 | 解决留存与现场弱网 |
| C7 | 原生 Android App（深链/后台/推送/离线） | 阶段 2 | 内嵌设备桥轮询，支持定时开播 |
| C8 | iOS 支持 | 阶段 3+ | 明确降级，不承诺一键播放 |

## 6. 非功能需求

| 类别 | 要求 | 度量 |
|---|---|---|
| 一致性 | 标注与卡片必须可复现 | κ ≥ 0.60 / α ≥ 0.70 / 字段一致率 ≥ 80% |
| 可复现 | 同输入同规则集两次生成重合 | ≥ 90% |
| 性能 | 生成歌单 | ≤ 3 秒（60 分钟场，本地规则） |
| 可靠性 | 现场可用 | 离线可打开 plan；无网仅损失跳转播放 |
| 安全 | 设备桥令牌一对一、动作白名单、注册安装码 | 无任意命令执行能力 |
| 隐私 | 偏好与历史本地优先；模型调用只传场合与曲名 | 不传身份信息 |
| 合规 | 不托管音频、不提供下载、仅索引与跳转 | 版权风险隔离 |

## 7. 数据契约（摘要，全文见氛围体系 §6）

四个对象：`track`（曲目 + 8 轴 + confidence + source）、`venue_card`（场合卡，含 rationale/status）、
`rule`（编号 + 条件 + 结论 + 理由 + 版本）、`plan`（锁定后不可变，带 rule_version）。

三条硬约束：
1. `confidence` 必填——推断元数据不能当实测值。
2. `familiarity` 必须绑定人群定义。
3. `plan` 记录规则集版本，保证可回溯。

## 8. 指标树

**北极星指标**：**周有效场次** = 生成 plan 且实际连续播放 ≥ 30 分钟的次数。

| 层级 | 指标 | 目标（阶段 1） |
|---|---|---|
| 获客 | 链接打开 → 选卡完成率 | ≥ 60% |
| 价值 | 首播成功率（给出建议后实际点播） | ≥ 70% |
| 价值 | 不切歌率（90 秒内未切） | ≥ 60% |
| 效率 | 决策完成时间（选卡到开播） | ≤ 60 秒 |
| 质量 | 编排生成可用率 | ≥ 50% |
| 质量 | 现场跳过率 | ≤ 15% |
| 留存 | 7 日复用率 | ≥ 30% |
| 变现 | 付费试点门店数 | ≥ 3 |

## 10. 本期不做（明确排除）

| 不做 | 理由 |
|---|---|
| 自动混音 / 生成 mix 成品 | DJ.Studio 已极致，重资产且偏离"找歌" |
| 曲库 / 版权 / 播放器 | 重资产、法律风险，会变成"又一个音乐 App" |
| 专业 DJ 功能（打碟、Cue、Loop、BPM 拉伸） | 目标用户是小白 |
| 通用手机操作（发微信、订票、控家居） | 手机厂商智能体的绝对领地 |
| UGC 歌单社区 / 评论 / 关注 | 冷启动无内容，与网易云正面冲突 |
| 听歌识曲（音频指纹） | Shazam/ACRCloud 成熟，调用即可 |
| 多音乐平台同时支持 | 先跑通酷狗（已真机验证），再抽象 |
| 微信小程序首发 | **平台限制：小程序不能拉起站外 App**，播放断一层 |
| iOS 一键播放承诺 | Safari 对第三方 scheme 限制严格 |
| 现场实时 BPM 分析 / 节拍匹配 | 属 DJ 软件领域，且现场不允许算法不确定 |
| 硬件播放盒 | B 端验证 20 家以上再议 |
| 付费体系（C 端） | 留存未验证前不做商业化 |

## 11. 风险与待验证假设

| 风险 / 假设 | 影响 | 对策 / 验证 |
|---|---|---|
| **H3：场合→参数映射无跨人群共识** | 判断层不成立，产品根基动摇 | M0 盲评实验，最便宜的一次证伪 |
| 酷狗深链协议变更 | 播放链路中断 | 多通道降级（已实现）+ 协议检测 |
| iOS 无法唤起 | 一半用户无法一键播 | 明确降级路径，不承诺 |
| 中文曲目 BPM/Camelot 元数据缺失 | 曲库扩充成本剧增 | 抽样 20 首调接口验证（H4） |
| 现场手机操作成本高 | 临场段不可用 | 关灯环境单手实测（L4） |
| 能量曲线可视化对小白无意义 | 编排台核心界面失效 | 让用户指认"这里不对"（L2） |
| 上游 Mobile Agent 接口变动 | fork 维护成本 | 增量收敛在单 Provider + assets |

## 12. 变更记录

**v1.0（2026-11-04 上午）**：确立"场景 → 音乐 → 一键播放"定位；P0-P2 功能分级；六条已验证事实基线；
M1-M6 里程碑。

**v2.0（2026-11-04 中午）**：
1. 定位收紧为"DJ Agent：把场合翻译成歌单"，明确不是播放器/曲库/打碟软件。
2. 新增**判断层**为首要资产（8 轴 + 场合卡 + 12 条规则 + 一致性门槛 κ/α）。
3. 功能结构改为**生命周期三段**（分场景 / 场前编排 / 临场使用），取代原 P0-P2 平铺。
4. 落地形态定为 **H5/PWA 优先 → Android App → B 端控制台 → 生态**，明确排除小程序首发与 iOS 一键播放承诺。
5. 新增**北极星指标**（周有效场次）与分层指标树。
6. 新增"不做清单"12 项（含平台限制导致的排除）。
7. 新增**风险与待验证假设**表，H3 为 Kill 级假设。

## 附录 A：已验证事实基线（勿凭印象推翻）

1. **深链协议**：`kugou://start.weixin?{"cmd":212,"jsonStr":{"hash":"...","filename":"...","extname":"mp3"}}`
   URL 编码后经 `am start` 或「系统功能」深链通道唤起，小米 10S 实测**唤起并自动播放指定曲目**。
2. **标识符**：`hash`（32 位十六进制）深链必需；分享链 HTML 源码含全部 ID；`mixsong_id` 与
   `album_audio_id` 编码不通用、无法换算。
3. **搜索接口**：`http://mobilecdn.kugou.com/api/v3/search/song` 免 key 可用（必须 http）。
4. **包名**：`com.kugou.android`。
5. **Mobile Agent v0.2.0**：支持 skills + 「系统功能」深链打开；不接受任意 shell。
6. **无效 mixsong id 静默回落首页不报 404**，校验只能比对页面标题。

详细记录：[kugou-ids.md](kugou-ids.md)、[android-launch.md](android-launch.md)、[no-browser-launch.md](no-browser-launch.md)。

## 附录 B：术语

- **判断层**：8 轴 + 场合卡 + 规则集，输出 plan 的无界面资产。
- **场合卡（Venue Card）**：把口语固化成结构化字段的可复用场合定义。
- **plan**：锁定后的曲目序列 + 理由 + 规则版本，现场的唯一输入。
- **周有效场次**：北极星指标，生成 plan 且连续播放 ≥30 分钟的次数。
- **κ / α**：标注一致性的统计量（Cohen's kappa / Krippendorff's alpha），衡量"内部认同"是否成立。
