# 氛围体系（Ambience System）：一套可共识、可标注、可计算的 DJ 场合语言

> 版本 v0.1 ｜ 2026-11-04 ｜ 状态：体系设计稿（未写产品代码）
> 解决的问题：团队对"这个场合该放什么"没有共同语言，推荐结果无法评审、无法复现、无法培训。
> 定位：这是产品的判断层数据资产——功能可以被抄，共识体系不能。

---

## 1. 为什么需要这套体系（问题定义）

当前状态：推荐靠个人直觉 + 少量标签（场景名、能量、人声/器乐）。后果有三个，且都是"内部认同"缺失导致的：

| 症状 | 根因 | 体系如何解决 |
|---|---|---|
| 两个人对同一场合给出完全不同的歌单，谁也说服不了谁 | 没有共享的判定标准 | 每个轴给"判定问题"与档位定义，可逐条对照 |
| 同一句需求，今天推 A 明天推 B | 输入没有被结构化 | 场合卡（Venue Card）把口语固化成字段，结果可复现 |
| 新人无法上手，只能模仿老人 | 判断过程不可见 | 理由由轴值 + 规则生成，可讲解、可培训 |
| 评审只能吵"我觉得不对" | 没有可度量的目标 | 一致性指标（α / κ）+ 盲评胜率作为验收标准 |

**核心主张**：先建"词"，再建"规则"，最后才建"算法"。词不统一，算法越强越分裂。

---

## 2. 体系结构：四层翻译链

```
场合层（Where/Who/When）
   ↓ 翻译规则（可解释）
氛围层（8 个可听感轴，人话可判）
   ↓ 映射规则（区间约束）
音乐层（BPM / Key / 结构 / 人声占比）
   ↓ 编排规则（顺序与过渡）
时间层（能量曲线 + 换歌节奏）
```

设计原则：
1. **上层用人话，下层用参数**。用户只说场合，系统负责翻译，绝不要求用户懂 BPM。
2. **每层可单独评审**。场合卡标错、氛围标错、参数映射错，三类错误分开定位。
3. **每个结论可回溯**。一条推荐理由必须能指回具体的轴值与规则编号。

## 3. 受控词表 v1（8 个轴）

每个轴包含：判定问题（一句人话，标注员照此判断）、档位、锚点示例、常见误判。

### 轴 1｜场合类型 Venue（枚举，单选）

判定问题：**"这是在哪、为谁放？"**

| 档位 | 定义 | 锚点 |
|---|---|---|
| `home_solo` 独自居家 | 一人，无社交 | 深夜写代码、周末打扫 |
| `home_social` 居家社交 | 2-8 人，熟人 | 朋友来家吃饭 |
| `work_focus` 工作专注 | 需要认知投入 | 办公室、自习 |
| `work_public` 工作公共 | 开放办公/共享空间，有交谈 | 公司开放区、联合办公 |
| `venue_commercial` 商业空间 | 陌生客人流动 | 咖啡馆、买手店、餐厅 |
| `event_party` 聚会派对 | 以音乐/社交为主 | 生日会、小型 after party |
| `event_ceremony` 仪式场合 | 有流程与情绪要求 | 婚礼、追悼、毕业礼 |
| `outdoor_motion` 户外运动 | 伴随身体活动 | 跑步、骑行、健身 |
| `transit` 通勤移动 | 移动中、嘈杂 | 地铁、开车 |

### 轴 2｜交谈负荷 Conversation Load（1-4）

判定问题：**"音乐能不能抢人说话？"**

| 档 | 定义 | 音乐处置 |
|---|---|---|
| 1 静默场合 | 不能有音乐或仅极轻 | 纯环境音/极低密度 |
| 2 背景可谈 | 说话不用提高音量 | 人声少、密度低、无强钩子 |
| 3 可谈可听 | 愿意分神听 | 可有人声，副歌允许出现 |
| 4 音乐主导 | 音乐是主角，说话靠吼 | 强节奏、强钩子、高能量 |

### 轴 3｜能量 Energy（1-7）

判定问题：**"如果这段音乐是一个人，他的兴奋程度是几？"**（用锚点曲目校准，不用形容词）

| 档 | 体感 | 音乐特征参考 |
|---|---|---|
| 1 | 近乎静止 | 环境音、单音铺底、无鼓 |
| 2 | 安静呼吸 | 慢速钢琴/吉他，60-80 BPM |
| 3 | 轻微律动 | 80-100 BPM，轻鼓或 shaker |
| 4 | 稳定前进 | 100-115 BPM，四踩底鼓出现 |
| 5 | 明显上扬 | 115-125 BPM，副歌推进 |
| 6 | 高能 | 125-135 BPM，密集编排 |
| 7 | 全开 | 135+ BPM 或强失真/大 drop |

### 轴 4｜温度 Warmth（1-3）

判定问题：**"听起来是暖的还是冷的？"**

1 冷（合成器、金属感、空旷混响）｜2 中性｜3 暖（模拟、木质、人声靠近）

### 轴 5｜密度 Density（1-3）

判定问题：**"同一时刻有多少层声音在动？"**

1 稀疏（≤3 层，留白多）｜2 中等｜3 饱满（多轨叠加、几乎无留白）

### 轴 6｜人声 Vocal（1-4）

判定问题：**"人声占多大位置？"**

1 纯器乐｜2 气声/采样碎片（不成句）｜3 正常演唱（人声为乐器之一）｜4 人声主导（唱是主体）

### 轴 7｜熟悉度 Familiarity（1-4）

判定问题：**"听众大概多熟？"**

1 全新（首发/冷门独立）｜2 冷门（圈内知道）｜3 有点耳熟（听过但叫不出名）｜4 大众熟歌（能跟唱）

> "别放太熟的歌" = 熟悉度 ≤2，这是场景需求里出现频率最高的约束之一。

### 轴 8｜锐度 Edge（1-3）

判定问题：**"听起来扎不扎耳朵？"**

1 柔和（无失真、高频收敛）｜2 中性｜3 锋利（失真、攻击性鼓、工业感）

## 4. 场合卡（Venue Card）：把口语固化成结构化输入

一张卡 = 一个可复用、可评审、可复现的场合定义。

### 4.1 字段规范

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `card_id` | string | ✓ | `vc-<slug>-<n>`，如 `vc-cafe-afternoon-1` |
| `name` | string | ✓ | 人话名，如"周六下午咖啡馆" |
| `venue` | enum(轴1) | ✓ | 场合类型 |
| `audience` | string | ✓ | 谁在场，人数范围、年龄构成 |
| `conversation` | int 1-4 | ✓ | 交谈负荷 |
| `energy_curve` | enum | ✓ | `ramp` 爬坡 / `plateau` 平台 / `wave` 波浪 / `descend` 回落 / `pulse` 脉冲 |
| `energy_range` | [int,int] | ✓ | 能量区间，如 [3,5] |
| `warmth` | [int,int] | ✓ | 温度区间 |
| `density` | [int,int] | ✓ | 密度区间 |
| `vocal` | [int,int] | ✓ | 人声区间 |
| `familiarity` | [int,int] | ✓ | 熟悉度区间 |
| `edge` | [int,int] | ✓ | 锐度区间 |
| `duration_min` | int | ✓ | 时长（分钟），决定歌单长度与换歌节奏 |
| `hard_constraints` | string[] | ✗ | 硬约束，如"不能有脏话""不能有钟声" |
| `rationale` | string | ✓ | 一句话说明"为什么这样定"，供评审 |
| `status` | enum | ✓ | draft / reviewed / canonical |

## 5. 映射规则：氛围 → 音乐参数

规则以"编号 + 条件 + 结论 + 理由"形式固化，评审只审规则，不审个案。

| 规则号 | 条件 | 结论 | 理由 |
|---|---|---|---|
| R-01 | `conversation ≤ 2` | `vocal ≤ 2` 且 `density ≤ 2` | 人声歌词与说话竞争注意力 |
| R-02 | `conversation = 1` | 仅允许 `vocal = 1` 且 `energy ≤ 2` | 静默场合音乐只做空气 |
| R-03 | `conversation = 4` | `energy ≥ 5` 且 `edge ≥ 2` | 音乐主导时需要有推力 |
| R-04 | `venue = work_focus` | `vocal ≤ 1`、`energy ∈ [2,3]` | 认知负荷高，歌词破坏专注（有实证支持：歌词任务干扰阅读） |
| R-05 | `venue = venue_commercial` 且 `duration ≥ 90` | `energy_range` 跨度 ≥ 2 | 长时段单能量会疲劳 |
| R-06 | `venue = event_ceremony` | `edge = 1`、`hard_constraints` 必填 | 仪式场合容错极低 |
| R-07 | `venue = outdoor_motion` | `energy ≥ 5` 且 BPM ≥ 120 | 需匹配步频/心率 |
| R-08 | `familiarity = [1,2]`（"别太熟"） | 排除近 90 天热门 Top 200 | 熟悉约束是显式需求 |
| R-09 | 任意 | 相邻曲目 BPM 差 ≤ 6，Camelot 同调或 ±1 | 过渡听感下限 |
| R-10 | `energy_curve = ramp` | 首曲能量 = 区间下限，末曲 = 上限，单调不降 | 曲线语义 |
| R-11 | `energy_curve = plateau` | 全程能量差 ≤ 1 | 曲线语义 |
| R-12 | `energy_curve = wave` | 每 20-30 分钟一个 ±1.5 的起伏 | 曲线语义 |

> 规则数量先控制在 12 条以内。规则越多越难达成共识，宁可漏也不可乱。

## 6. 数据模型（契约草案，非实现）

```json
{
  "$schema": "ambience-system/v1",
  "track": {
    "id": "string (hash)",
    "title": "string", "artist": "string",
    "bpm": "number", "camelot": "string (1A-12B)",
    "energy": "int 1-7", "warmth": "int 1-3", "density": "int 1-3",
    "vocal": "int 1-4", "edge": "int 1-3",
    "familiarity": "int 1-4 (需按人群定义，非绝对)",
    "tags": ["string"], "verified": "boolean",
    "source": "manual | tunebat | api | inferred",
    "confidence": "number 0-1"
  },
  "venue_card": { "...": "见 §4.1" },
  "rule": { "id": "R-xx", "when": "expression", "then": "constraint", "why": "string", "version": "string" },
  "plan": {
    "card_id": "string", "tracks": ["id"], "duration_min": "number",
    "energy_series": ["int"], "explanations": ["string"],
    "generated_by": "ruleset-version"
  }
}
```

三条契约约束：
1. `confidence` 必填——推断出来的元数据不能当实测值用。
2. `familiarity` 必须绑定人群定义（"对 25 岁一线城市人群的熟悉度"），否则无意义。
3. `plan.generated_by` 记录规则集版本，保证结果可复现、可回溯。

## 7. 内部认同机制（这是"公司内部认同"的落地部分）

体系不是写出来的，是**对齐出来的**。四步：

### 第 1 步：术语卡（1 页 A4，全员必读）
8 个轴 × 判定问题 × 档位 × 锚点曲。要求：新人 10 分钟内能独立标注 10 首歌，与老手一致率 ≥ 70%。

### 第 2 步：双人盲标 + 一致性度量
- 样本：50 首（覆盖 9 类场合、中英文各半）
- 每人独立标注 8 轴，不讨论
- 计算一致性：
  - 有序轴（能量/密度/人声/熟悉度/锐度）：加权 Cohen's κ，**门槛 κ ≥ 0.6**
  - 场合类型（名义）：Krippendorff's α，**门槛 α ≥ 0.7**
- 未达门槛的轴：不是"标注员不行"，而是**轴定义有问题**——重写判定问题，再测。

### 第 3 步：争议仲裁与规则修订
每条分歧记录：轴、两人取值、各自理由。每周 60 分钟对齐会，只处理 κ 最低的两个轴。修订必须落到词表版本号（v0.1 → v0.2）。

### 第 4 步：冻结与发布
达到门槛后冻结为 `v1.0`，此后新增曲目按 v1.0 标注；规则集同步打版本，任何推荐结果可指回 `ruleset-v1.0`。

### 认同的验收标准（可量化，不靠感觉）

| 指标 | 定义 | 目标 |
|---|---|---|
| 标注一致性 | 50 首双人盲标的加权 κ | ≥ 0.60 |
| 场合卡一致性 | 10 人对同一场合卡独立填字段，字段一致率 | ≥ 80% |
| 推荐可复现 | 同输入同规则集，两次生成歌单重合度 | ≥ 90% |
| 盲评胜率 | 体系生成 vs 直觉挑选，5 人盲评 | ≥ 70% 偏好体系 |

## 8. 这套体系为什么是护城河

1. **它不是功能，是资产**：50 首标注 + 9 张场合卡 + 12 条规则，是几个月对齐的产物，竞品抄功能抄不走共识。
2. **它让模型可替换**：判断来自规则与轴值，换模型不影响结论稳定性——这正好解决"同一句需求今天推 A 明天推 B"。
3. **它是可教的产品**：理由由轴值和规则编号生成，用户看到的是"因为你在咖啡馆、需要交谈，所以选了纯器乐、能量 3"，而不是一段玄学文案。
4. **它能长成标准**：如果未来 B 端客户（咖啡馆/健身房/婚礼策划）采用这套场合卡，它就从内部语言变成行业语言。

## 10. 待验证假设（体系本身的风险）

| # | 假设 | 若不成立的后果 | 验证方式 |
|---|---|---|---|
| H1 | 8 个轴足以区分绝大多数场合 | 需要加轴（如"语言""时代感"） | P1 标注后看残差：同一卡内分歧集中在哪 |
| H2 | 非专业用户能稳定判断"能量/密度/人声"三轴 | 标注成本过高，体系无法规模化 | P1 的 κ 值 |
| H3 | "场合→参数"映射存在跨人群共识 | 产品判断层不成立（研究稿 U6） | P3 盲评胜率 |
| H4 | 中文曲目的 BPM/Camelot 元数据可得 | 曲库扩充成本剧增 | 抽样 20 首调接口核对 |
| H5 | 用户能理解并信任"轴值式理由" | 理由价值不成立 | 用户访谈 10 人 |
